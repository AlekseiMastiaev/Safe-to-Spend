# AGENTS.md

Инструкции действуют для всего репозитория. Отвечай на языке пользователя.

## Быстрый контекст

- Safe to Spend — Vue 3 + TypeScript приложение для месячного бюджета.
- Сборка: Vite. Состояние UI: Pinia. Маршрутизация: Vue Router.
- Постоянные данные: Dexie/IndexedDB в локальном режиме или Supabase в облачном.
- Тесты: Vitest + Vue Test Utils, окружение `jsdom`.
- Пакетный менеджер: npm. Версия Node зафиксирована в `.nvmrc` (`22.22.2`).
- Production base path: `/Safe-to-Spend/`; маршруты используют hash history.

## С чего начинать

Не читай весь репозиторий. Сначала найди затронутые файлы через `rg`/`rg --files`, затем
открывай только ближайшие реализации, тесты и один релевантный документ.

| Задача | Сначала смотреть |
| --- | --- |
| Финансовые правила, суммы, даты месяца | `docs/domain.md`, `src/domain/`, соседние `__tests__` |
| Хранение и транзакции | `src/shared/persistence/`, затем `src/shared/db/` и/или `src/shared/supabase/` |
| Экран или компонент | соответствующий файл в `src/views/` или `src/components/` и соседний тест |
| Глобальное UI-состояние | `src/stores/` |
| Навигация | `src/router/` |
| Авторизация или облачный режим | `docs/cloud-setup.md`, `src/stores/auth.ts`, `src/shared/supabase/` |
| Схема Supabase/RLS | `supabase/migrations/` и `docs/cloud-setup.md` |
| Архитектурное решение | релевантный файл в `docs/adr/` |
| Команды, запуск, деплой | `package.json`, `README.md`, `.github/workflows/` |

## Архитектурные инварианты

Сохраняй эти правила; подробные обоснования находятся в `docs/adr/`.

1. `src/domain` содержит чистую TypeScript-логику и не импортирует Vue, Pinia, Dexie,
   Supabase или DOM API.
2. Компоненты не обращаются к Dexie или Supabase напрямую. Чтение и запись идут через
   контракты и репозитории из `src/shared/persistence`.
3. Pinia хранит только разделяемое временное UI-состояние. Постоянные финансовые данные
   не дублируются в store.
4. Все денежные значения хранятся целыми числами в копейках. Проверяй целочисленность,
   безопасный диапазон и используй функции из `src/domain/money.ts`.
5. Фактически оплаченная сумма обязательства вычисляется из истории платежей и отдельно
   не сохраняется.
6. Для открытого обязательства резерв равен `max(план − факт, 0)`; для закрытого — `0`.
   Перерасход допустим. Частичный платёж ниже плана не меняет безопасный остаток.
7. Финансовые итоги вычисляются из исходных записей и не сохраняются как второе состояние.
8. Локальный и облачный режимы должны соблюдать одинаковые repository-контракты и доменные
   правила. Они выбираются при сборке и не объединяют данные автоматически.
9. Несколько сумм во вводе поддерживают только сложение; не используй `eval`. Каждое
   слагаемое становится отдельным платежом, а операция записи должна быть атомарной.

## Правила изменений

- Делай минимальный, сфокусированный diff; не меняй несвязанные файлы.
- Не редактируй `dist/`, `node_modules/`, кеши и другие генерируемые файлы.
- Не меняй `package-lock.json`, если зависимости не изменялись намеренно.
- Следуй существующему стилю: 2 пробела, LF, без `;`, одинарные кавычки, ширина 100.
- Используй alias `@/` для импортов из `src`, когда это делает импорт понятнее.
- При изменении поведения добавь или обнови ближайший тест. Для исправления ошибки сначала
  зафиксируй воспроизводящий сценарий тестом, когда это практично.
- Изменение доменного правила требует синхронизации `docs/domain.md`, тестов и, если меняется
  принятое решение, соответствующего ADR или нового ADR.
- Изменение модели хранения должно учитывать оба backend-а и миграцию/обратную совместимость.
- Не добавляй секреты. Во frontend допустим только Supabase publishable key; никогда не
  используй `service_role`, secret key или OAuth Client Secret.
- Не выполняй разрушительные операции с пользовательскими финансовыми данными без явного
  запроса и подтверждённого безопасного пути восстановления.
- Каждую завершённую правку обязательно оформляй отдельным коммитом и отправляй в текущую
  ветку через `git push`. Перед коммитом проверь diff и не включай чужие или несвязанные
  изменения. Если commit или push невозможен, явно сообщи причину и оставшееся действие.

## Проверки

Используй самую узкую проверку во время работы, затем достаточный набор перед завершением.

```sh
# Один тестовый файл
npm run test -- src/domain/__tests__/calculations.spec.ts

# Все тесты
npm run test

# Статический анализ и типы
npm run lint
npm run typecheck

# Полная production-проверка
npm run build
```

Для изменения только Markdown достаточно проверить diff и ссылки. Для кода минимум —
затронутые тесты и `npm run typecheck`; для сквозных, persistence- или build-изменений —
`npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`.

## Экономия времени и токенов

- Не пересказывай документацию в ответе; указывай только изменённые файлы, результат проверок
  и существенные риски.
- Не открывай `dist/`, `node_modules/`, lock-файл или весь `docs/`, если задача этого не требует.
- Перед созданием нового helper/composable/component найди существующий аналог через `rg`.
- Для внешней библиотеки сначала определи её точную версию из `package.json`/lock-файла, затем
  используй Context7 только для нужного API. Не запрашивай общую документацию без необходимости.
- Предпочитай существующие доменные функции, repository-контракты и тестовые helpers новым
  абстракциям.
- Не запускай полный набор проверок после каждой мелкой правки: сначала точечная проверка,
  полный набор — один раз перед сдачей, когда он нужен по риску.

## Формат завершения задачи

Кратко сообщи:

1. Что изменено.
2. Какие проверки выполнены и их результат.
3. Что не проверено или какие риски остались.

Добавляй `Assumptions: ...` только если допущения существенно повлияли на результат.
