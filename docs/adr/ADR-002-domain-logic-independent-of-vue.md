# ADR-002: Доменная логика не зависит от Vue

- Статус: принято
- Дата: 2026-08-07

## Контекст

Финансовые правила Safe to Spend должны одинаково работать в Web, PWA, Android и iOS. Они включают расчёт фактических платежей, оставшегося резерва, безопасного остатка, экономии, перерасхода и дневного лимита.

Если разместить эти правила внутри Vue-компонентов или `computed`, их будет сложно тестировать, переиспользовать и изменять независимо от интерфейса.

## Решение

Финансовая логика реализуется чистыми TypeScript-функциями доменного слоя.

Доменный слой:

- принимает данные через аргументы;
- возвращает вычисленный результат;
- не читает и не изменяет IndexedDB;
- не импортирует Vue, Pinia, Dexie или DOM API;
- не хранит вычисляемые итоги;
- для одинакового ввода возвращает одинаковый результат.

Примеры доменных функций:

```ts
calculateActualPaid(payments);
calculateRemainingReserve(obligation, payments);
calculateBudgetSummary(input);
calculateDailyAllowance(input);
parseMoneyAdditionExpression(value);
```

UI отвечает за ввод и отображение. Use case координирует пользовательскую операцию. Repository отвечает за получение и сохранение данных.

## Последствия

Положительные:

- финансовые правила тестируются без браузера и базы;
- Vue-компоненты остаются небольшими;
- одна логика используется на всех платформах;
- пограничные случаи фиксируются быстрыми unit-тестами;
- замена UI-технологии не требует переписывать финансовую модель.

Отрицательные:

- данные нужно явно преобразовывать в доменные входные структуры;
- разработчик должен соблюдать границы слоёв;
- часть кода распределяется между UI, use case и доменом, а не находится в одном компоненте.

## Рассмотренные альтернативы

### Расчёты внутри Vue-компонентов

Отклонена: связывает бизнес-правила с жизненным циклом UI и усложняет тестирование.

### Сохранение готового BudgetSummary в базе

Отклонена: итог может рассинхронизироваться с доходами, обязательствами, платежами и свободными расходами.
