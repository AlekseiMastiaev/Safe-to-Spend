# ADR-003: Dexie и IndexedDB являются источником постоянных данных

- Статус: принято
- Дата: 2026-08-07

## Контекст

Приложению требуется постоянное локальное хранение нескольких связанных коллекций: месяцев, доходов, шаблонов, обязательств, платежей, свободных расходов и настроек.

Одновременное хранение полной копии финансовых данных в Pinia и IndexedDB создаст два конкурирующих состояния.

## Решение

IndexedDB является источником постоянных финансовых данных. Dexie используется как типизированный слой доступа к IndexedDB.

Поток записи:

```text
Component
  → Use case
  → Repository
  → Dexie
  → IndexedDB
```

Поток чтения:

```text
IndexedDB
  → Repository query
  → Composable
  → Component
```

В этом MVP Pinia хранит временное состояние интерфейса, например:

- выбранный месяц, синхронизированный с route;
- глобальные уведомления;
- временное состояние навигации;
- открытый диалог, если он управляется глобально.

Доходы, обязательства, платежи и свободные расходы не дублируются в Pinia как отдельный постоянный источник.

Компоненты не обращаются к объекту Dexie напрямую. Доступ к таблицам изолируется repository-контрактами.

## Границы состояния приложения

Локальное состояние одного экрана остаётся в его компоненте. Pinia нужен для состояния интерфейса, которое используют несколько несвязанных компонентов или страниц. Постоянные пользовательские данные принадлежат IndexedDB, а вычисляемые финансовые значения получаются из них через доменные функции. Серверного состояния в MVP нет: финансового backend нет.

| Значение | Где находится | Правило |
| --- | --- | --- |
| `selectedMonthKey` | Pinia как текущий выбор в рамках приложения | Это ссылка на бюджетный месяц, а не копия его записей. Когда месяц указан в URL, после проверки параметра выбор в Pinia приводится к URL; два независимых значения не поддерживаются. Сами месяцы хранятся в IndexedDB. |
| Состояние навигации | Текущий экран — Vue Router; открытие локального меню — состояние его компонента | Активный маршрут не копируется в Pinia. Pinia понадобится только для элемента навигации, которым действительно управляют несвязанные части приложения. |
| Очередь уведомлений | Pinia | Сообщения нужны нескольким страницам, но являются временными: после перезагрузки очередь пуста. |
| Тема интерфейса | Сейчас — системная схема через CSS; при ручном выборе — настройка в IndexedDB | Выбор пользователя должен переживать перезагрузку. Pinia не становится вторым записываемым источником настройки; UI получает актуальное значение через слой чтения настроек. |

Безопасный остаток, фактически оплаченная сумма, резерв, экономия и перерасход не записываются ни в Pinia, ни в IndexedDB как отдельные итоги: они вычисляются из актуальных доходов, обязательств, платежей и свободных расходов. Pinia сам по себе не означает постоянное хранение; возможные механизмы его сохранения не меняют выбранный для MVP источник финансовых данных.

## Последствия

Положительные:

- после перезагрузки используется одно авторитетное состояние;
- реактивное чтение может обновлять UI после изменений базы;
- repository можно заменить тестовым double;
- транзакции и запросы сосредоточены в инфраструктурном слое;
- компоненты не зависят от схемы IndexedDB.

Отрицательные:

- для реактивного UI требуется адаптер или composable поверх запросов;
- ошибки базы должны проходить через use case до понятного сообщения;
- транзакционные операции нескольких таблиц требуют явной реализации.

## Рассмотренные альтернативы

### Pinia как основное хранилище с последующей синхронизацией

Отклонена: появляется риск рассинхронизации и неопределённый порядок восстановления состояния.

### Прямые вызовы Dexie из компонентов

Отклонена: UI становится связанным со схемой базы, транзакциями и деталями запросов.

### localStorage

Отклонена из-за отсутствия подходящей модели коллекций, индексов и транзакций.
