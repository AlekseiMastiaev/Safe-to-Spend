# ADR-009: История платежей является источником фактической суммы

- Статус: принято
- Дата: 2026-08-07

## Контекст

Плановая сумма обязательного расхода может отличаться от фактической. Коммунальные услуги могут оплачиваться несколькими счетами, бензин — несколькими покупками, а итог может оказаться ниже или выше плана.

Хранение одновременно платежей и изменяемого поля `actualPaid` создаст два представления одного факта, которые могут рассинхронизироваться.

## Решение

`MonthlyObligation` хранит план и состояние завершения:

```ts
interface MonthlyObligation {
  plannedAmount: Money;
  isSettled: boolean;
  settledAt: string | null;
}
```

Каждая фактическая оплата хранится отдельной записью:

```ts
interface ObligationPayment {
  id: string;
  monthId: string;
  obligationId: string;
  amount: Money;
  paidAt: string;
  note: string | null;
}
```

Поле `actualPaid` не сохраняется:

```text
actualPaid(i) = сумма платежей обязательства i
```

Оставшийся резерв вычисляется так:

```text
если расход закрыт:
    remainingReserve(i) = 0
иначе:
    remainingReserve(i) = max(plannedAmount(i) − actualPaid(i), 0)
```

Расход закрывается явно, когда новых платежей не ожидается. Закрытие ниже плана освобождает экономию. Повторное открытие восстанавливает недостающий резерв. Перерасход разрешён и уменьшает безопасный остаток.

Если пользователь вводит выражение с несколькими слагаемыми, каждое слагаемое создаёт отдельный `ObligationPayment`. Все записи одной операции сохраняются атомарно.

## Последствия

Положительные:

- сохраняется полный состав фактической суммы;
- поддерживаются платежи в разные даты;
- отдельный платёж можно изменить или удалить;
- итог невозможно рассинхронизировать с историей;
- экономия, перерасход и остаток резерва вычисляются однозначно;
- резервная копия сохраняет историю, а не только итог.

Отрицательные:

- для отображения обязательства нужно агрегировать связанные платежи;
- удаление обязательства или месяца должно транзакционно удалять платежи;
- импорт обязан проверять связи `monthId` и `obligationId`;
- UI требует доступной истории платежей.

## Рассмотренные альтернативы

### Одно изменяемое поле actualPaid

Отклонена: теряется история отдельных оплат и их дат.

### Платежи вместе с сохранённым actualPaid

Отклонена: появляется дублирование и риск рассинхронизации.

### Автоматическое закрытие при достижении плана

Отклонена: фактические расходы могут превысить план или завершиться ниже него. Только пользователь знает, ожидаются ли новые платежи.
